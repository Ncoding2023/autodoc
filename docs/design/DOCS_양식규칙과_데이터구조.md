# DOCS 양식 규칙과 데이터 구조

2026-10-23 · 구현 순서 1단계 · 범위: Database → Entity

## 핵심 규칙

각 항목은 연결 키, 표시 이름, 입력 형식, 순서를 갖는다. 입력값은 문서별로 보관한다.
연결 키는 DOCX의 위치를 찾는 기준이며 변경하지 않는다. 화면에서 바꾸는 항목명은 표시 이름이다.

예를 들어 연결 키 `담당자`를 유지하면서 표시 이름을 `담당자`에서 `업무자`로 변경한다.
입력값 `김담당`은 그대로 유지한다. 이 변경으로 항목이 추가되거나 배치가 이동하지 않는다.

## 양식 파일의 입력 표시

항목명까지 변경하려면 이름 자리와 내용 자리가 구분되어 있어야 한다. 첫 지원 양식은 다음처럼 준비한다.

```text
{{담당자.label}}: {{담당자}}
{{담당업무.label}}: {{담당업무}}

{{업무절차.label}}
{{업무절차}}

{{주의사항.label}}
{{주의사항}}
```

`{{담당자.label}}`에는 표시 이름, `{{담당자}}`에는 입력값을 넣는다.
따라서 실제 결과는 `업무자: 김담당`이 된다. 원본에 쓰인 일반 문자열 `담당자`를 문서 전체에서 찾아 바꾸지 않는다.

- 키는 한글 완성형 또는 영문으로 시작하고 한글 완성형·영문·숫자·밑줄을 사용한다. 최대 100자이며 대소문자를 구분한다.
- 중괄호 안에 공백을 넣지 않는다. `.label`은 항목명 위치를 나타내는 예약 접미사다.
- 초기 업로드는 각 키에 항목명 표시와 내용 표시가 모두 있는 양식을 받는다. 짝이 없거나 문법이 잘못되면 위치를 안내하고 재업로드하도록 한다.
- 같은 키가 여러 번 나오면 하나의 항목으로 묶는다. 모든 위치에 같은 항목명·입력값을 반영한다.
- 순서는 본문에서 내용 표시가 처음 나타난 순서로 1부터 부여한다. 이후 작성 중 순서를 바꾸지 않는다.
- 첫 단계의 탐색·치환 대상은 DOCX 본문 문단과 표 셀의 문단이다. Word 내부에서 글자가 여러 run으로 나뉘어도 같은 문단의 표시로 인식해야 한다.
- 머리글·바닥글·텍스트 상자·각주 등에서 발견된 입력 표시는 초기 범위에서 지원하지 않는 위치로 안내한다. 지원하지 않는 표시가 출력에 그대로 남은 상태를 성공으로 처리하지 않는다.
- 로고 등 변경하지 않는 내용은 그대로 둔다. 반복 표·이미지 입력·수식·조건문 표기는 초기 범위에서 제외한다.

처음 제공한 `{{담당자}}` 예시는 내용 자리만 표현했다. 항목명 변경 요구사항을 반영하면서 `.label` 자리를 추가한 것이다.
양식 등록자는 샘플 DOCX로 준비 방법을 확인한다. 작성자는 이 표기를 직접 다루지 않는다.

## 표시 이름과 입력 형식

- 표시 이름은 최대 100자로 보관한다. 초기 이름은 연결 키에서 가져오고 11번 화면에서 바로 수정한다.
- 지원 형식: `TEXT` 짧은 글, `LONG_TEXT` 긴 글, `DATE` 날짜.
- 값은 텍스트로 보관하고 날짜는 `YYYY-MM-DD`로 저장한다. 형식 검증은 후속 DTO·Service 단계에서 수행한다.
- 항목별 필수 설정은 두지 않는다. 내용 미입력은 허용한다. `NULL`은 미입력이며 생성 시 빈 문자열로 처리한다.
- 문서 제목은 문서 목록에서 구분하는 이름이다. 템플릿 이름, 원본 파일명, DOCX 내부 제목과 별개다.

## 저장 구조

### 기존 테이블 재사용

`document_templates`는 템플릿 이름·소유자·DOCS/SHEETS 구분과 준비 상태를 보관한다.
`template_files`는 원본 파일의 경로·원래 이름·저장 이름·크기·체크섬을 보관한다.
원본 바이트를 데이터베이스에 넣지 않는다. 저장소의 실제 파일과 메타데이터를 연결한다.

### template_fields · 양식의 항목 정의

- `template_field_id`: 항목 ID.
- `template_id`: 해당 템플릿의 ID. FK 제약조건은 사용하지 않는다.
- `field_key`: 변경하지 않는 연결 키.
- `field_label`: 등록 시 설정한 기본 항목명.
- `field_type`: 짧은 글 / 긴 글 / 날짜.
- `field_order`: 표시 순서.
- `created_at`, `updated_at`: 생성·수정 시각.

템플릿별 키와 순서는 각각 중복될 수 없다. 기존 JSON `structure_data`와 `template_style_data`는 유지한다.
새 DOCS 항목의 기준은 `template_fields`로 통일하고, 같은 정보를 JSON에 중복 저장하지 않는다.
기존 SHEETS 구조는 기존 JSON과 열·행 테이블을 계속 사용한다.

### document_fields · 개별 문서의 항목 사본과 값

- `document_field_id`, `document_id`: 개별 문서의 항목 식별 정보.
- `field_key`, `field_label`, `field_type`, `field_order`: 작성 시작 시 양식 정의에서 복사한 값.
- `field_value`: 해당 문서에서 입력한 내용.
- `created_at`, `updated_at`: 생성·수정 시각.

문서별 키와 순서는 각각 중복될 수 없다. 작성 중 바꿀 수 있는 값은 항목명과 내용이다.
키·형식·순서는 유지한다. 항목 정의를 복사하므로 템플릿 변경이나 다른 문서 편집과 분리된다.
표시 이름 변경으로 키를 다시 만들거나 기존 값을 다른 키로 이동하지 않는다.

### documents.source_template_file_id · 사용한 원본 양식

작성 시작 시 사용한 `template_files`의 ID를 보관한다. 기존 문서에는 `NULL`을 허용한다.
원본 파일은 제자리에서 덮어쓰지 않으며 구조를 바꾸려면 새 템플릿으로 등록한다.
문서 생성 시 현재 템플릿의 최신 파일을 임의로 찾아 쓰지 않고 문서가 참조한 원본을 사용한다.
해당 원본을 참조하는 문서가 남아 있다면 파일을 물리 삭제하지 않는 정책을 후속 파일 Service에 적용한다.
이는 기존 문서 생성의 재현성을 위한 원본 참조이며 문서 버전 기능은 아니다.

## 이후 구현 시 지킬 흐름

1. 업로드를 검증하고 입력 표시를 탐색한다. 항목이 없거나 지원하지 않는 표시가 있으면 안내한다.
2. 템플릿과 원본 파일 정보, 추출한 항목 정의를 저장한다. 파일 생성/DB 저장 실패 시 임시 파일을 정리한다.
3. 작성 시작 시 소유권·DOCS 형식·원본 준비 상태를 확인하고 문서와 항목 사본을 하나의 트랜잭션으로 저장한다.
4. 작성 중 항목명과 내용을 같은 입력 화면에서 편집한다. 저장할 때 문서 소유권과 전체 키 집합을 확인한다.
5. 새 항목 추가·기존 항목 삭제·키 변경·필드 형식/순서 변경 요청은 받지 않는다. 빈 내용은 허용한다.
6. 저장된 항목명과 내용을 원본 표시 위치에 넣어 DOCX를 생성한다. 미리보기에도 같은 데이터를 사용한다.
7. 항목명과 값이 다른 문서·템플릿에 영향을 주지 않는지, 저장 실패 시 일부 값만 반영되지 않는지 검증한다.

권한과 존재 여부는 Service에서 검증한다. Entity를 API에 직접 반환하지 않는다.
화면에서 사용자에게 연결 키나 저장 경로를 편집하도록 노출하지 않는다.

## DB 반영과 호환성

추가 SQL: `docs/database/migrations/20261023_01_docs_fields.sql`.
현재 저장소에는 자동 마이그레이션 도구가 없으므로 해당 SQL은 기존 PostgreSQL 스키마에 명시적으로 적용한다.
자동 실행 SQL이나 새 마이그레이션 프레임워크는 추가하지 않는다.

이 단계는 새 테이블 2개와 nullable 열 1개를 추가한다. 기존 고정 본문 값과 SHEETS 데이터는 변환·삭제하지 않는다.
기존 생성·조회·수정 API는 그대로 유지된다. 새 항목 구조를 API에 연결하는 일은 후속 단계다.
새 DOCS 기능을 활성화하기 전에는 문서 삭제 시 `document_fields`도 같은 트랜잭션에서 정리하도록 기존 Service를 확장해야 한다.
